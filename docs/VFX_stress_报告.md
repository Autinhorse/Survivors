# §23 独立 VFX 压力测试 · 报告

对应需求：`docs/GODOT_3D_可行性验证需求.md` §23，风险清单见 §15，动态光策略见 §16
数据：`benchmark/results/ALL_results.csv`（`run` 列标记 `S23 ...` 的行）
前置：敌人架构已定为 mm-merged（M5），本轮固定 1000 敌人 / 阴影 B

---

## 1. 为什么要单独测

§23 明确要求把敌人数量测试和 VFX 压测分开，理由在实测后更清楚了：
**两者的瓶颈完全不同。** 群体是 CPU（draw call 提交、Transform 更新），
VFX 是 GPU（overdraw、填充率、透明层数）。混在一起测，
任何一方的结论都会被另一方污染。

负载等级按 §23：

| Level | 并发弹体 | 爆炸/秒 |
|---|---|---|
| 0 | 0 | 0 |
| 1 | 100 | 10 |
| 2 | 300 | 30 |
| 3 | 500 | 50 |
| 4 | 1000 | 100 |

「弹体」按**并发数**控制而不是发射速率 —— 同屏并存的数量才是成本，§23 给的也是并发数。
其中 5% 是火箭（网格弹体 + 持续烟迹，昂贵的那种），其余是曳光弹（便宜的那种）。

## 2. 结果

### 2.1 在 1000 敌人之上叠加 VFX

| Level | 帧时 | 1% low | GPU | draw calls |
|---|---|---|---|---|
| 0 | 1.05 ms | 1.22 ms | 0.40 ms | 332 |
| 1 | 1.26 ms | 1.41 ms | 0.43 ms | 452 |
| 2 | 1.46 ms | 1.63 ms | 0.47 ms | 570 |
| 3 | 1.63 ms | 1.81 ms | 0.52 ms | 654 |
| 4 | **1.77 ms** | 1.96 ms | 0.61 ms | 655 |

### 2.2 VFX 单独（0 敌人）

| Level | 帧时 | GPU |
|---|---|---|
| 0 | 0.69 ms | 0.35 ms |
| 1 | 0.92 ms | 0.39 ms |
| 2 | 1.14 ms | 0.43 ms |
| 3 | 1.30 ms | 0.48 ms |
| 4 | 1.48 ms | 0.57 ms |

**VFX 的净成本：叠加在 1000 敌人上是 0.72 ms，单独跑是 0.79 ms —— 基本相同。**
也就是说群体和 VFX 的开销是**可加的，互不干扰**。这是个有用的结论：
两边可以分别定预算，不需要担心耦合。

Level 4（1000 弹体 + 100 爆炸/秒 + 1000 敌人）总计 1.77 ms，
在这台开发机上是 565 FPS。

## 3. 最重要的一条：每次爆炸开动态光的代价

§16 建议「不要每个爆炸都创建真实动态光源」。这条建议现在有数字了。
Level 2（300 弹体 / 30 爆炸每秒，约 10 盏并发光）：

| | 帧时 | GPU | 1% low |
|---|---|---|---|
| 不开动态光（§16 的做法） | 1.46 ms | **0.47 ms** | 1.63 ms |
| 每次爆炸开一盏 OmniLight | 1.84 ms | **1.08 ms** | 2.27 ms |
| 差值 | +0.38 ms | **+0.61 ms（GPU 翻 2.3 倍）** | +0.64 ms |

对照一下量级：**整个 Level 4 的粒子负载（1000 弹体 + 100 爆炸/秒）只让 GPU 涨了 0.21 ms，
而 Level 2 下区区 10 盏动态光就让 GPU 涨了 0.61 ms —— 大约是前者的 3 倍。**

而且这是在 Level 2 测的；Level 4 会有约 35 盏并发光，代价还要再翻几倍。

> **结论：§16 的建议不仅成立，而且是本次实验里性价比最高的一条优化。**
> 发光感必须来自 emission + 粒子 + Glow。动态光要留给少数关键对象（Boss、玩家武器蓄力等），
> 并且要有数量上限。

这也是整个 benchmark 里**唯一一处 GPU 成为主要增量**的地方 —— 值得注意。

## 4. §23 要求的瓶颈定位

§23 问：瓶颈来自 crowd simulation / geometry / draw calls / shadows / particles /
transparency / projectile / 其他？答案：

| 候选 | 实测结论 |
|---|---|
| geometry（面数） | **不是**。16,000 单位时 GPU 才 1.17 ms（M5） |
| crowd simulation | **曾经是**，用传统 Node 时。换成 mm-merged 后降到 0.10 ms/1000 单位 |
| draw calls | **曾经是**，Node 架构 2000 单位近 2 万次。MultiMesh 后固定约 300 |
| shadows | **中等**。小兵真实投影在 1000 单位时 +59%（M4），已改用 blob |
| particles / transparency | **目前不是**，但这是**目标硬件上最不确定的一项**（见 §5） |
| projectile 数量 | **不是**。1000 并发弹体走 MultiMesh，成本很低 |
| **dynamic lights** | **是**。10 盏光 = 3 倍于整个 Level 4 粒子负载的 GPU 成本 |

## 5. 这份数据的边界

1. **RTX 5080 上 overdraw 几乎免费。** 这台机器的填充率高得离谱，
   §15 点名的 smoke overdraw / additive blend / 透明层数在这里根本压不出来。
   **在 Iris Xe / 780M 上这一项的结论很可能完全不同** —— 这是整个 benchmark 里
   目标硬件差异最大的部分，因为它是纯填充率问题。
2. **爆炸是撒在 22 m 半径的圆内的**，重叠程度有限。
   §15 特别点名的「大量重叠爆炸」没有被充分复现 ——
   真实玩法里爆炸会聚集在玩家周围，overdraw 会比这里更集中。
   要复现这个，需要一个把爆炸挤在小区域内的变体。
3. 分辨率固定 1886×1061。overdraw 成本与像素数成正比，
   4K 下所有 VFX 数字要乘以约 4 倍。

## 6. 一个静默失败的坑（重要）

手动投放粒子时，我最初用 `amount_ratio = 0` 来阻止发射器自动发射。
**`amount_ratio` 会连粒子池一起归零**，`emit_particle()` 拿不到槽位，
一个粒子都不发 —— 而且不报任何错误。

后果非常危险：测量数字看起来完全正常（Level 4 只多花 0.68 ms），
如果不截图核对，就会得出「VFX 几乎免费」的**错误结论**并写进报告。

正确写法：`emitting = false` + `emit_particle()`，停掉自动发射但保留粒子池和模拟。

**教训：性能测试必须配合视觉核对。** 一个没有真正产生负载的压测，
读数一样漂亮 —— 而且比真实结果更漂亮。

---

## 7. 顺带的架构改动

M3 的粒子系统是 10 个 one-shot 发射器环形复用，在 100 爆炸/秒下每股烟都会被
提前打断，测出来的烟量远低于真实值。把池子扩到 200 个发射器又会变成
在测发射器节点本身的开销。

改为**每类效果一个发射器 + `emit_particle()` 手动投放**：
并发爆炸数没有上限，一个 draw call，同时也是正式项目该用的写法。
