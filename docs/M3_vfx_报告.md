## 1. 已实现的三类武器

| 武器 | 速率（§22 建议值） | 组成 |
|---|---|---|
| Machine Gun | 10 发/秒 | 枪口闪光 + 曳光弹 + 命中火花 + 命中闪光 |
| Rocket | 2 发/秒 | 可见弹体（自发光）+ 烟迹 + 爆炸火球 + 地面冲击波环 + 碎片 + 火花 |
| Tesla / Electric | 1 次/秒 | 电弧 + 命中闪光（冷色）+ 链式传导到最近 2 个目标 |

外加：敌人还击（见 §3）、被击中的顿挫反馈、死亡爆炸与重生。

---

## 2. 架构：一开始就是池化 + 批处理的

M3 的产出会直接进入 §23 的压力测试（最高约 1000 弹体 / 100 爆炸每秒）。
如果每发子弹都 `new` 一个节点，M4/§23 量到的将是分配器而不是渲染器。所以：

| 系统 | 实现 | 说明 |
|---|---|---|
| 曳光弹 | **1 个 MultiMesh** + 打包浮点数组（位置/速度/生命） | 上限 768 发，1 次 draw call |
| 闪光 / 火球 / 冲击波环 | 每类 1 个 MultiMesh（上限 256） | 逐实例颜色做淡出 |
| 火花 / 烟 / 碎片 | 一小组 one-shot `GPUParticles3D` 环形复用 | 14 / 10 / 8 个发射器轮转 |
| 火箭 | 池化节点 + 持续发射的拖尾 | 上限 24 枚 |
| 电弧 | **1 个 `ImmediateMesh`**，每帧重建全部电弧 | 水平带状，适配 60° 机位 |

`scripts/vfx/VfxCommon.gd`（材质/网格/粒子工厂）、`scripts/vfx/VfxManager.gd`（池 + 更新）、
`scripts/units/CombatDirector.gd`（按 §22 速率驱动）。

### 关于动态光（§16）

**默认不为爆炸创建任何动态光**，发光感全部来自 emission + 粒子 + Glow。
`VfxManager.explosion_light` 保留为开关，目的不是拿来用，而是让 M4 能实测
"每次爆炸开一盏真光"要多花多少 —— 把这件事变成数字而不是争论。

## 3. 一处超出 §22 字面要求的实现：敌人还击

§22 只要求玩家的三种武器。但 M3 的通过标准里有**"信息可读"**这一条，
单向开火根本无法判断可读性 —— 参考图里满屏都是交叉火力。
所以加了敌人还击（`enemy_fire`，可关闭）：曳光弹射向机甲附近的**散布点**而非精确命中，
因为完全汇聚的弹道看起来像激光秀而不是交火。

仍然是纯表现：不伤害玩家、没有血量、没有 AI、没有寻路。
敌人的缓慢位移同理，只为让战场不是静态布景，真正的移动/AI 属于 M4。

## 4. 踩到的坑

1. **静态函数用全局类名调用自己** —— `VfxCommon.gd` 内部写 `VfxCommon.curve_tex(...)`，
   直接 `godot <scene>` 运行时类缓存尚未建立 → 编译失败 → 每帧刷错误，表现为**进程假死**。
   同一个坑 M2 的 `ProcMesh` 已经踩过一次，这次换了个形式又踩：
   **脚本内部互相调用一律不要用全局类名**，用 `preload` 或不加限定。
2. **无贴图的粒子是硬边白方块**：`QuadMesh` + 均匀 alpha，看起来像白纸片而不是烟。
   解决办法是在代码里程序生成软边精灵（径向衰减 + 噪声打散），项目仍然零贴图文件。
3. **叠加混合极易过饱和**：颜色给到 (7, 4, 1.6) 时所有效果都糊成白色，武器之间失去区分度。
   降到 2–3.5 的量级后色相才留得住，"烫"的感觉交给 Glow 去做。
4. **低模球体做火球会露馅**：加色球体在这个尺寸下读起来是个扁八边形。
   火球改成软边公告板精灵。
5. **截图工具不能在 headless 下跑**：`--headless` 时 `RenderingServer.frame_post_draw`
   永不触发，`await` 会永久挂起。截图/计时必须开窗口跑（已写进工具注释）。

## 5. 性能（RTX 5080，仅供 A/B，非目标硬件）

| 场景 | 平均帧时 | draw calls | 三角形 |
|---|---|---|---|
| M2 静态场景 | 0.655 ms | 556 | 210,242 |
| **M3 战斗进行中** | **0.680 ms** | 608 | 235,794 |

当前强度（10 + 2 + 1 发/秒，26 个敌人还击）下 VFX 只增加约 0.025 ms。
这个数字**不能**用来推断 §23 的压力测试结果 —— 那里的量级要大 10–100 倍，
而且真正的风险在 overdraw 和透明层数（§15），不在 draw call。

## 7. 需要人工判断（§22 通过标准）

> 动态战斗应：足够热闹；武器有区分；信息可读；不依赖大量高成本动态光；
> 特效质量达到可接受商业游戏水平。

我的判断供参考：

- **武器区分度**：够。曳光弹是快速细橙线，火箭是慢速弹体 + 烟迹 + 大火球，
  电弧是冷色瞬闪 + 链式 —— 三者在静帧里都能一眼分辨。
- **信息可读**：加了敌人还击之后成立；但敌人本身仍是 primitive 占位，
  等 M4/M5 换成真正的小兵模型后需要重新评估。
- **热闹度**：按 §22 的建议速率是"有秩序的交火"，还不是参考图那种满屏弹幕。
  参考图是战斗峰值瞬间；要达到那个密度需要提高速率或增加同时开火的敌人数 ——
  这属于 §23 压力测试的范畴，不建议现在为了好看而调高速率，否则 M4 的基线就不干净了。
- **最弱的一环**：爆炸的烟还偏薄，火焰缺少上升的火舌；这两项是继续投入回报最高的。
