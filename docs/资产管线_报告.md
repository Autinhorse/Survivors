## 1. 我做了哪一半，没做哪一半

§21 的完整链条是：

    Reference / Prompt → AI 3D → Blender → Cleanup → 减面/Retopo
        → Scale/Origin 统一 → Material 统一 → GLB → Godot Import

**没做的：AI 3D 那一步。** 它需要外部服务（Meshy / Tripo / Rodin / Hunyuan3D 之类）
的账号和额度，我不该替你调用也不该替你花钱。

**做了的：AI 输出之后的全部环节。** 这一段才是决定 §33 D 项
「一个普通环境资产人工 Cleanup ≤ 30 分钟」的部分，而且它是确定性的 ——
所以它应该是脚本，不是手工点击。手工点永远做不到稳定达标。

为了让这一半在**真实难度**下被验证，我造了三个刻意复现 AI 输出毛病的替身
（`tools/make_test_assets.py`），而不是拿干净模型糊弄过去：

- 2.5–8 万面的三角汤，没有可用拓扑
- 任意缩放（26–310 m，不是米制），原点在世界中心而不是底面
- 物体带任意世界偏移（模型飘在离原点几十米处）
- 部分面法线翻转、孤立顶点
- 随机命名的材质

§21 指定的三件测试资产都做了：一组 Rock（5 块）、一座 Bridge、一个 Mech。

## 2. 管线

`tools/asset_pipeline.py`，Blender 无头运行，吃任意 `.glb/.gltf/.obj/.fbx/.blend`：

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| import | 按扩展名分派 | — |
| cleanup | 合并重复点、消退化面、删孤立点、重算法线、三角化 | 用 **bmesh** 而不是 `bpy.ops.mesh.*`：前者跨版本稳定，且不依赖编辑模式和选中状态（无头运行时后者极易出错） |
| decimate | COLLAPSE 到目标面数 | §4.1 的预算：小型单位 100–300 面 |
| scale | 全体乘同一系数，最长轴对齐到目标米数 | `--fit object` 用于资产"组"：按整组包围盒缩放量到的是**摆放跨度**而不是石头本身 |
| origin | 每个物体的原点移到底面中心 | Godot 侧摆放时 y=0 就是地面，不用每个资产猜偏移 |
| recenter | 整组搬到世界原点，底面贴地 | 清掉 AI 输出自带的任意世界偏移 |
| material | 统一成一个命名材质 | AI 输出各带一个随机命名材质，直接进项目就没法批处理、没法做 Preset |
| export | GLB，Y-up | Godot 直接读 |

用法：

```
blender --background --factory-startup --python tools/asset_pipeline.py -- \
    --input raw.glb --output assets/environment/rocks.glb --name Rock \
    --target-tris 300 --target-size 2.4 --fit object --color "0.35,0.33,0.30"
```

每步耗时和网格统计都会打印，最后输出一行 JSON，方便汇总成表。

## 3. 结果

| 资产 | 物体数 | 面数 | 尺寸 | 全程耗时 | 输出 |
|---|---|---|---|---|---|
| Rock（一组 5 块） | 5 | 25,600 → **1,500**（300/块） | 161.7 m → 2.4 m | **0.60 s** | 153.6 KB |
| Bridge | 1 | 29,952 → **6,000** | 309.8 m → 13.0 m | **0.62 s** | 155.8 KB |
| Mech | 1 | 15,360 → **2,500** | 26.0 m → 3.6 m | **0.51 s** | 66.6 KB |
| HeavyRock（吞吐测试） | 1 | 81,920 → **300** | 43.1 m → 2.6 m | **1.30 s** | 31.1 KB |

Godot 侧导入零报错。验收截图里可以确认：比例正确（对照 1 m / 2 m 参照方块）、
全部贴地（原点在底面）、材质统一、减面后轮廓仍然可读。

按 HeavyRock 的耗时外推，30 万面的输入约 4–5 秒。**吞吐不是瓶颈。**

## 4. 过程中发现的两个真问题

这两个都是"人工 cleanup 时间"的真正来源 —— 如果靠手工，它们每次都会重现：

1. **AI 输出自带的世界偏移必须清掉。** 只把网格内部的原点挪到底面是不够的，
   物体本身还在离原点几十米的地方。在 Godot 里的表现是
   「放在 (0,0,0) 的东西不在 (0,0,0)」，而且每个资产的偏移都不一样。
2. **缩放物体时必须同时缩放它们的位置。** 否则一组石头会各自缩小，
   但彼此间距不变 —— 五块石头被摊开到 138 m 外。

还有一个是我自己造测试件时踩的，但它在真实资产里同样常见：
**`join()` 会把其他物体烘进活动物体的局部空间**，活动物体如果还带着非等比缩放，
被烘进来的部件就会按该缩放的倒数变形（我的桥墩被拉成了 18 倍高）。
合并前必须先 apply transform。

## 5. 这个管线**没有**覆盖的部分

必须写清楚，否则会被当成"D 项已完成"：

1. **贴图与 UV。** 当前实现把材质统一成纯色，直接丢弃了 UV 和烘焙贴图。
   真实 AI 3D 输出通常带一张烘焙贴图 —— 要保留就需要保 UV、
   重新烘焙或做图集，这部分完全没做。
   本项目 M2 的美术方向是纯色 + 程序噪声，暂时不需要；但正式项目如果要用贴图，
   这是最大的缺口。
2. **Retopo。** 只有 decimate（collapse），没有重拓扑。
   Decimate 对石头这类有机形体够用，对需要干净边流的主角/Boss 不够。
3. **LOD 与碰撞体。** 都没生成。Godot 4 导入时可自动生成 mesh LOD；
   碰撞体可以靠 glTF 节点命名后缀（`-col` / `-convcol`）自动生成 ——
   两者都是低成本补充，但当前脚本没做。
4. **风格一致性。** §21 要求记录"风格一致性"，而这只有在真实 AI 输出上才谈得上。
5. **减面预算必须匹配特征尺寸。** 第一次跑桥的时候我给了 1,600 面，
   细长的栏杆直接崩成尖刺。有机形体（石头）300 面就够，
   带细结构的（桥、机械）需要显著更高的预算，或者改用手工低模。
   **这不是可以一个数字包打天下的参数。**

## 6. 对 §33 D 项的结论

> D. Production Pipeline：普通 3D 环境资产可以高效产出，
> 人工 Cleanup 时间理想目标 ≤ 30 分钟。

**部分达成，尚未闭合。**

- **AI 输出之后的全部环节：已自动化，单个资产 0.5–1.3 秒，人工时间约等于零。**
  剩下的人工只有：选三个参数（目标面数 / 目标尺寸 / 颜色）+ 目视验收，
  几分钟量级，远低于 30 分钟。
- **AI 生成本身：完全没有数据。** 生成耗时、成本、轮廓质量、风格一致性、
  是否需要重做 —— 这些才是 30 分钟预算里真正的不确定项，全部依赖你去测。

**要闭合 D 项，需要你提供的东西：** 用任意一个 AI 3D 服务生成
§21 指定的三件资产（一组 Rock、一座 Bridge、一个 Mech），
把原始输出（glb/obj/fbx 均可）丢给这个脚本，记录：

1. 生成一个资产花了多少时间 / 多少额度；
2. 输出的轮廓质量是否可用（这一步无法自动判断）；
3. 三个资产之间风格是否一致；
4. 跑完管线后是否还需要人工返工，返工多久。

第 1、3、4 项是纯记录；第 2 项需要人眼。管线这边已经准备好了。

## 6b. 第三条路径：程序化建模（已用于本项目）

除了「清理外来网格」，还有一条对本项目更合适的路径：**直接用脚本把资产长出来**。
`styles/<风格>/assets.py`，同样是 Blender 无头运行。

理由：目标图是 stylized low-poly —— 强轮廓、清晰色块、模块化复用。
这种风格要的正是规整几何和统一比例，而这恰好是 AI 3D 最不擅长的。
参数化还顺带消灭了 §21 点名的风险项：**风格一致性是白送的**，
不是需要额外验证的东西。§20 本来就把「程序生成」列为合法来源。

已产出并接进正式场景（替换掉 M2 的纯色盒子建筑和"两个球"的树）：

| 资产 | 面数 | 说明 |
|---|---|---|
| house_small / large / tall | 296 / 344 / 320 | 石头地基、屋顶出檐与屋脊、门窗凹陷、转角立柱、门廊、烟囱 |
| trees（3 变体） | 188 / 208 / 188 | 树干有锥度和弯曲、粗枝、分层收拢的树冠 |

建筑是 M2 判定的最大视觉短板。上面每一样细节都只花几十个面 ——
真正让房子读起来像房子的不是面数，是**出檐的厚度**和**门窗的凹陷**。

树仍然走 MultiMesh 批处理：`ScatterField` 增加了 `source_scene`，
从 GLB 里取网格当变体。资产在 Blender 做，批处理在 Godot 做，两件事不冲突。

### 这一段踩到的三个坑

1. **Blender 的 Base Color 是线性的，Godot 的 albedo_color 是 sRGB。**
   同一组数字直接搬过去，整体会被明显提亮（0.318 当 sRGB 是深橄榄，
   当线性是浅卡其）。写入 Blender 前必须转换。
2. **资产文件的粒度决定了能不能单独摆放。** 三栋房子导出成一个 GLB，
   Godot 侧实例化一次就会把三栋全带进来 —— 摆三栋会变成场景里有九栋。
   单体资产一个文件；只有走 MultiMesh 按变体取用的"组"（石头、树）才适合合并。
3. **空闲的粒子池也要付钱。** §23 为压测加的大容量手动投放发射器
   （8192+8192+4096）即使一个粒子都不发，缓冲区每帧照样被绘制 ——
   实测正式场景白烧 **16.4 万三角形/帧**。已改为 `mass_pool` 开关，
   默认 0（不创建），只有压测场景打开。

## 7. 复跑

```
# 程序化生成本项目资产（房屋 / 树）
blender --background --factory-startup --python styles/<风格>/assets.py --     --out-dir assets/environment --only buildings,trees

# 生成脏输入（没有 AI 服务时的替身）
blender --background --factory-startup --python tools/make_test_assets.py -- --out-dir tmp/raw

# 过管线
blender --background --factory-startup --python tools/asset_pipeline.py -- \
    --input tmp/raw/raw_rocks.glb --output assets/environment/rocks.glb \
    --name Rock --target-tris 300 --target-size 2.4 --fit object

# Godot 侧验收
Godot_v4.7-stable_win64.exe --path <project> res://scenes/AssetPipelineCheck.tscn
```
