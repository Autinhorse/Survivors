## 1. 执行顺序

M2 拆成两步，顺序是刻意的：

| 步骤 | 内容 | 回答的问题 |
|---|---|---|
| **M2-A** | 材质 / 着色器 / 光照 / 地面装饰（模型不动） | Godot 渲染器本身能不能出商业画面 |
| **M2-B** | 低模资产替换 primitive（石头 / 树 / 灌木） | 轮廓质量 |

先 A 后 B，是因为 A 才是真正的渲染器验证；B 属于资产生产。
按 §21，Blender / AI 3D 资产管线**单独验证**，不在 M2 里阻塞渲染结论 ——
所以 M2-B 的低模是在 Godot 里程序化生成的，可直接复用已有材质、零导入风险。

## 2. M2-A：材质 / 着色器 / 光照

### 新增着色器（`shaders/`）

| 文件 | 用途 | 关键点 |
|---|---|---|
| `ground.gdshader` | 地形（地面 + 河岸 + 崖壁） | 世界空间投影而非 UV（CSG 的 UV 按面切分不可用）；按**坡度**自动在草地和岩石之间过渡，一个材质同时覆盖地面和崖面 |
| `ground_patch.gdshader` | 土路 / 空地色块 | 噪声扰动的径向遮罩吃掉方块边缘，重叠的小块自然连成一条土路 |
| `water.gdshader` | 河流 | 滚动噪声法线 + Fresnel + 岸边泡沫 + 流动白花；**刻意不用 DEPTH_TEXTURE / SCREEN_TEXTURE**，泡沫带由网格 UV 推导，Mobile 渲染器上更安全也更便宜 |
| `foliage.gdshader` | 树冠 / 灌木 | 逐物体风摆（相位取自实例世界坐标，避免整片同步摆动）+ 噪声打散 + 底部压暗做体积感 |
| `grass_tuft.gdshader` | 地面草丛 | 风摆 + 距离缩放淡出；`INSTANCE_CUSTOM` 携带逐实例的颜色/高度/相位抖动 |

### 材质

- 石头 / 木头 / 墙面 / 屋顶：`StandardMaterial3D` + **世界空间三平面投影**的噪声贴图。
  用世界空间（而非局部）是必要的：所有 primitive 都被非等比缩放过，局部投影会让纹理密度随物体大小乱变。
- 噪声贴图由 `FastNoiseLite` + `Gradient` 色阶在场景内生成，不依赖任何外部贴图文件。

### 地面：贴图 + 凹凸，不是几何草（实测修正）

**第一版做错了**：铺了 26000 丛真几何草。放大参考图后可以确认那是错的 ——
参考图的开阔草地是一张**平面贴图**：机甲的影子投在上面是完整干净的剪影，
没有任何草叶打断它，草的纹理粒度均匀且明显在平铺。3D 几何只留给石头，
以及少量成簇的小植物点缀（靠近石堆和土路边缘）。

实测代价（RTX 5080，1886×1061，600 帧采样）：

| 方案 | 平均帧时 | 场景三角形 |
|---|---|---|
| 26000 丛几何草 | 0.693 ms | 300,058 |
| 完全不放草 | 0.620 ms | 200,002 |
| **贴图 + 凹凸 + 2600 丛点缀（当前）** | **0.655 ms** | **210,242** |

也就是说几何草单独吃掉了 **10 万面，占整个场景三角形的三分之一**。
对照 §5 给 1000 个敌人的预算是 1000 × 300 = 30 万面 ——
地面装饰吃掉了敌人预算的三分之一，而且这 10 万面每帧还要跑带 4 次 `sin()` 的风摆顶点着色器。
顶点吞吐和带宽正是 Iris Xe / 780M 最弱的地方，在集显上这笔开销的占比只会更难看。

当前做法：

- **草纹在 `ground.gdshader` 里**：ridged 分形噪声（细而亮的纹路像草叶，
  普通平滑噪声做不出这个），3 次采样同时提供颜色打散和**凹凸法线**的梯度 ——
  整个"草叶层"的成本是 3 次纹理采样，不是 10 万个三角形；
- 凹凸只在坡度够平的地方生效（崖壁不需要草的凹凸）；
- `scripts/environment/GrassField.gd` 保留为**点缀植物簇**：2600 丛，成簇分布，
  只出现在石堆、路边等参考图里确实有模型的位置。

这条同时是给 M4/M5 的教训：**在开始压测之前，先确认几何预算没有被装饰性内容悄悄吃掉。**

### 光照 / 后处理

- 1 盏 `DirectionalLight3D`（暖色，能量 1.8，阴影 opacity 0.92，3 级 CSM）；
- 天空环境光 0.42 + 程序天空（暖地平线）；
- ACES tonemap、Glow、轻微深度雾、饱和度/对比度微调。

> **Mobile 渲染器的硬限制**：不支持 SSAO / SSIL / SDFGI / 体积雾。
> §22 里「可选 SSAO」在 Mobile 下不可用，深度雾是这里唯一可用的空间层次手段。
> 如果后续认为 SSAO 对画面必要，那本身就是一条「需要 Forward+ 高画质 Preset」的证据（§10）。

## 3. M2-B：程序化低模资产

`scripts/environment/ProcMesh.gd` + `ScatterField.gd`

- 石头 / 灌木 / 树冠 / 树干全部程序生成，**平面着色**（flat shading）：
  在这个机位下轮廓和切面才是可读信息，平滑法线没有价值；
- 每类 4–6 个变体，按变体分桶成若干 MultiMesh 绘制；
- 顺带的好处：环境道具**已经是批处理的**，M4/M5 的群体测试量到的是敌人开销，不是场景开销。

面数：石头约 100–130 tri，树冠约 400 tri，灌木约 130 tri。

## 4. 踩到的坑（都已修复，记录以免重复）

这一轮大部分时间花在下面五个问题上，全部是「渲染出来不对但引擎不报错」的类型：

1. **三角形缠绕方向**：我按网格顺序生成的三角形与 Godot 的正面约定相反。
   结果是近侧面被背面剔除，从上往下看到的是壳体**内壁** —— 石头渲染成中空的黑色多边形。
   法线数值检查（93 面朝外 / 6 面朝内）是「对的」，因为法线和缠绕是两回事。
2. **球体两极退化**：极点那一圈顶点都在轴上，但我给了它们各自不同的随机位移，
   于是极点三角扇变成细长片、法线朝侧面，顶面照不到光。极点必须共用同一个位移。
3. **逐顶点扰动过大**：会把壳体打成高频碎面，一半面背光，物体整体发黑。
   低频形变要占主导，逐顶点抖动只能是点缀。
4. **草丛投影**：26000 丛草每丛都投影，画面上是一层黑色星形碎屑 ——
   看上去像草的颜色错了，其实是它们自己的影子。地面装饰必须关投影（也对应 §17 的结论）。
5. **`cull_disabled` 下的背面法线翻转**：草叶是竖直面、法线朝上，
   从背面看时 Godot 会把法线翻成朝下 → 完全不受光。在片段着色器里强制取地面法线解决。

另外沿用 M1 的一条：`.tscn` 的 `Transform3D` 是**按行**序列化的。

## 5. 当前渲染统计

固定镜头满屏（1886×1061，Forward Mobile）：

    draw calls   556
    primitives   ~210,000
    objects      556
    平均帧时      0.655 ms（RTX 5080，仅供 A/B 对比，非目标硬件）

draw call 主要来自仍然逐个 `MeshInstance3D` 的静态道具（桥板、栏杆、栅栏、箱子、敌人占位）。
这个数字现在不构成问题，但**是 M4/M5 的已知优化空间**，届时应先合批静态场景再评判敌人开销。

## 6. 与参考图仍存在的差距

按对画面影响从大到小：

1. **建筑没有细节**：门、窗、屋檐、茅草屋顶都还是纯色盒子 + 三棱柱；参考图的房子有明确的结构分层。
2. **没有大气层次**：参考图有夕阳方向光、暖色雾、轻微光晕；这里只有深度雾。
3. **玩家 / 敌人仍是 primitive 占位**（属于 M3 的范围，不在 M2 判据内）。
4. **河流没有急流 / 瀑布粒子**（§18 允许用 particle，属于 M3 VFX）。
5. **地面缺少小花草 / 碎石等第二层装饰**。

## 6b. Mobile vs Forward+ 实测对比（2026-08-20）

起因：体积雾对最终画面可能是必要的，而它是 Forward+ 独占。按 §35「用实测替代猜测」，
直接把渲染器切过去跑了一遍，而不是凭印象估。

### 迁移成本：一行项目设置

    renderer/rendering_method = "mobile"  ->  "forward_plus"

- 5 个自定义着色器**一行都没改**，零报错、零警告；
- 场景、材质、MultiMesh、脚本全部不用动；
- SSAO / 体积雾的参数可以和 Mobile 共存于同一个 `Environment`：
  Mobile 下引擎打一条 warning 然后忽略，实测开销完全不变（0.690 → 0.688 ms）。

所以「迁移」本身几乎没有成本。**真正的成本是依赖，不是切换。**

### 性能实测

RTX 5080 Laptop / 1886×1061 / 关闭 V-Sync / 90 帧预热 + 600 帧采样。
当前场景（无敌人群、无 VFX）：

| 配置 | 平均帧时 | 相对 Mobile |
|---|---|---|
| Mobile | 0.690 ms | 1.00× |
| Forward+（SSAO 和体积雾都关） | 1.570 ms | **2.28×** |
| Forward+ + SSAO | 1.784 ms | 2.59× |
| Forward+ + SSAO + 体积雾 | 1.865 ms | 2.70× |

关键结论：**开销的大头是渲染器基线（+0.88 ms），不是那两个特性（SSAO +0.21，体积雾 +0.08）。**

必须强调的免责：这是开发机数据，按 §11 不能作为性能判断依据。
而且 Forward+ 多出来的开销主要是 clustered lighting、深度预通道和额外中间缓冲，
也就是带宽和显存 —— 正好压在 Iris Xe / 680M / 780M 最弱的地方，
在目标硬件上这个 2.28× 很可能更差而不是更好。

### 一条硬约束

`rendering_method` 是**启动时读取的项目设置，运行时无法热切换**。
所以 §24 里的「High preset = Forward+」意味着改这一档画质要重启游戏。
这个约束需要在设计 Preset UI 之前就知道。

### Forward+ 相对 Mobile 多出来的能力

| 特性 | 对本项目的价值 |
|---|---|
| 体积雾 | **高** —— 目前唯一的真·大气层次手段 |
| SSAO | **中高** —— 接触阴影，物体和地面的关系明显更实 |
| SSIL / SDFGI | 低 —— 固定光照场景收益小，且很贵 |
| 屏幕空间反射 SSR | 低 —— 水面已用便宜方案（§18 本就不要求物理准确） |
| 次表面散射 | 无 —— 机械题材用不上 |
| TAA | 存疑 —— 大量粒子 + 快速弹道下容易拖影 |
| Clustered lighting（大量动态光） | 低 —— §16 本来就要求避免大量动态光 |

也就是说：真正想要 Forward+ 的理由基本只有**体积雾**和 **SSAO** 两项。

（附注：warning 显示 SSAO 在 **Forward+ 和 Compatibility** 下可用，唯独 Mobile 没有。）

### 当前处理方式

- 项目默认保持 **Mobile**（§10 的初始选择不变）；
- 生成器加了 `--forward-plus` 开关，用来产出 High preset 的 `Environment`：

      python tools/gen_greybox.py --forward-plus

- Forward+ 对比截图：`docs/reference/m2_forward_plus.png`。

### 建议的决策时机

**建议等 M4 之后再定，现在不迁移。** 理由：

1. 现在场景是空的 —— 没有 1000 个敌人，没有 VFX。在还不知道性能预算总量的时候，
   把基线渲染器换成贵 2.3× 的，等于提前把预算花掉；
2. M4 会给出「集显上 1000 敌人 + VFX」的真实开销，那时候 2.3× 才是可判断的数字；
3. 迁移成本既然是一行设置，就没有「提前迁移以降低风险」的必要 —— 风险本来就不在迁移上。

在此之前，大气层次用便宜手段做：深度雾 + 少量雾片几何 + glow。
如果最终判断这些替代方案达不到要求，那这件事本身就是
「本项目需要 Forward+ 高画质 Preset」的实证结论，而不是猜测。

## 7. 需要人工判断（§22 通过标准）

M2 的通过标准是主观的，文档明确要求人工判断：

> 截图不能再像「引擎测试场景」；达到参考画面约 70–80% 或更高的主观视觉完成度。
> 如果视觉不满意：停止后续性能测试，优先解决视觉问题。

请对比 `docs/reference/m2_visual.png` 和 `docs/target.png` 给出判断：

- **通过** → 提交 `M2 - visual quality`，进入 M3（战斗表现 / VFX）。
- **不通过** → 指出最不满意的 2–3 项，优先修视觉，不进 M3。

我的判断供参考：地面、水面、植被、光照已经脱离「引擎测试场景」的观感，
但**建筑细节**和**大气层次**这两项还明显拖后腿，是继续投入回报最高的地方。
