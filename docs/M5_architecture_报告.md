# Milestone 5 — 架构 / 优化比较 · 报告

对应需求：`docs/GODOT_3D_可行性验证需求.md` §22 Milestone 5，另见 §6、§7
数据：`benchmark/results/M5_architecture.csv`（每行都带 `run` 标记它来自哪次测量）
方法与 M4 相同：关 V-Sync，5 秒预热 + 20 秒采样，平均值与 1% low 分开

---

## 1. 比较了三种，而不是两种

§6 只要求比较传统 Node 与 Data-Oriented + MultiMesh。但 §7 另外问了一个问题：
CPU 批量 Transform、MultiMesh Instance Transform、Shader、Instance Custom Data，
**哪种组合才是赢家**。只测两种答不了这个问题，所以 MultiMesh 拆成了两个变体：

| 标识 | 架构 | 每单位的 CPU 工作 | draw calls |
|---|---|---|---|
| `node` | §6 方案 A：每单位 1 个 Node3D + 5 个 MeshInstance3D | 移动 + 3 个子节点 Transform | 5/单位 |
| `mm-parts` | 方案 B：5 个 MultiMesh（身/头/枪/左腿/右腿） | 移动 + **5 个部件 Transform**（含腿部摆动数学） | 5 总计 |
| `mm-merged` | 方案 B：合并成 **1 个网格 + 1 个 MultiMesh** | 移动 + **1 个 Transform**；腿摆和起伏在顶点着色器里 | 1 总计 |

三者几何完全相同（约 150 面/单位），满足 §22「使用尽可能相同的可见单位结构」。
两个 MultiMesh 变体都用 `set_buffer()` 整块写缓冲，而不是逐实例 `set_instance_transform()` ——
后者的每次调用开销正是要避开的东西，测它等于测错对象。

## 2. 主结果（阴影模式 B，敌人向玩家移动）

| 数量 | node | mm-parts | mm-merged |
|---|---|---|---|
| 500 | 1.92 ms / 2,622 dc | 1.45 ms / 301 dc | **0.74 ms** / 297 dc |
| 1000 | 4.25 ms / 5,113 dc | 2.60 ms / 301 dc | **0.79 ms** / 297 dc |
| 2000 | 10.64 ms / 10,073 dc | 4.99 ms / 301 dc | **1.02 ms** / 297 dc |

相对 node 的加速比：

| 数量 | mm-parts | mm-merged |
|---|---|---|
| 500 | 1.3× | 2.6× |
| 1000 | 1.6× | **5.4×** |
| 2000 | 2.1× | **10.4×** |

**加速比随数量增长而增长** —— 因为 node 的成本是线性叠加的，而 mm-merged 几乎是平的。

### 出货配置下的复测（2026-08-21）

上表是在 `spawn_radius = 30 m` 下测的 —— 那意味着**敌人有一部分是在屏幕内生成的**。
锁定可见范围（左右黑边）之后，屏幕外生成半径由相机推导为 **54.3 m**，
负载分布随之改变：单位铺得更开、在测量窗口内**几乎全程处于移动状态**
（1.6 m/s 走完 54 m 需要 34 秒），而之前有相当一部分已经抵达停止半径。

| 数量 | node | mm-parts | mm-merged |
|---|---|---|---|
| 500 | 2.50 ms / 1,692 dc | 1.90 ms / 329 dc | **1.05 ms** / 325 dc |
| 1000 | 5.11 ms / 3,917 dc | 3.08 ms / 329 dc | **1.20 ms** / 325 dc |
| 2000 | 11.99 ms / 8,124 dc | 5.45 ms / 329 dc | **1.55 ms** / 325 dc |

加速比 2.4× / 4.3× / 7.7×。**结论在一个明显不同的负载分布下复现了** ——
这比单纯重测更有价值，说明它不是某个特定配置的偶然。

一个值得注意的细节：node 架构的 draw call 从 10,073 降到 8,124（更多单位在屏幕外被剔除），
**帧时反而从 10.64 上升到 11.99 ms**。因为逐单位的 CPU 更新与是否可见无关，
而现在几乎所有单位都在移动分支里。这再次印证 §3.1：
**瓶颈是逐单位 CPU 工作，不是渲染。**

### 边际成本（每增加一个单位）

| 架构 | 每单位 |
|---|---|
| node | 6.4 µs |
| mm-parts | 2.4 µs |
| mm-merged | **0.37 µs** |

## 3. 收益来自哪里：一半一半

这是本轮最有价值的一条，因为它不是"用 MultiMesh 就好了"那么简单。

以 2000 单位为例拆解：

    node        10.64 ms
      ↓  -5.65 ms   脱离场景树 + draw call 从 10,073 降到 301
    mm-parts     4.99 ms
      ↓  -3.97 ms   5 次缓冲写 → 1 次；腿部数学从 CPU 搬到顶点着色器
    mm-merged    1.02 ms

**减少 draw call 只拿到约 59% 的收益，剩下 41% 来自减少逐单位 CPU 工作。**
换句话说：只把渲染换成 MultiMesh、但 CPU 仍然逐部件算 Transform，
在 2000 单位时只能从 10.64 ms 降到 4.99 ms —— 改善明显，但离"几乎免费"还差得远。

## 4. 更新循环的干净测量（补上 M4 的偏差）

M4 那次冻结对比是有偏差的：冻结后敌人不再走近玩家，被视锥剔除得更多，
draw call 从 5,135 掉到 3,749，差值里混进了"少画了一批"的部分。

这次把 `move_speed` 设为 0，冻结与否的可见单位数完全一致：

| 1000 单位 / 阴影 B / move=0 | 帧时 | draw calls |
|---|---|---|
| node，逻辑运行 | 4.42 ms | 3,706 |
| node，逻辑冻结 | 1.26 ms | 3,749 |
| **→ Node 更新循环的成本** | **3.16 ms** | — |
| mm-merged，逻辑运行 | 0.77 ms | 297 |
| mm-merged，逻辑冻结 | 0.67 ms | 296 |
| **→ MultiMesh 更新循环的成本** | **0.10 ms** | — |

**更新循环便宜了约 32 倍。**
另外注意一个直观的对照：**mm-merged 跑着逻辑（0.77 ms）比 node 完全冻结（1.26 ms）还快。**
也就是说 Node 架构哪怕一行游戏逻辑都不跑，光是场景树和 draw call 就已经输了。

## 5. MultiMesh 的上限在哪

继续往上加（§22：「如有必要继续提高」）：

| mm-merged 数量 | 帧时 | 1% low | GPU | draw calls |
|---|---|---|---|---|
| 2,000 | 1.02 ms | 1.31 ms | 0.48 ms | 297 |
| 4,000 | 1.80 ms | 2.22 ms | 0.55 ms | 297 |
| 8,000 | 3.27 ms | 3.80 ms | 0.71 ms | 297 |
| 16,000 | 6.19 ms | 7.24 ms | 1.17 ms | 297 |

**16,000 个单位仍有 162 FPS**，GPU 只用了 1.17 ms。
瓶颈依旧在 CPU —— 那个填缓冲区的 GDScript 循环。真要更高，下一步是把循环移出 GDScript
（C# / GDExtension）或用 compute shader 更新，但**目前完全没有这个必要**：
§4.1 的压力测试目标是 1500–2000，而 mm-merged 在 2000 时只花 1.02 ms。

## 6. 结论：正式项目小兵用哪种架构

> **Data-Oriented + MultiMesh，且必须是「合并网格 + Shader 动画」那一版（`mm-merged`）。**

理由：

1. 2000 单位时比传统 Node 快 **10.4 倍**，且加速比随规模继续扩大；
2. 敌人数量基本不再是约束条件 —— 1000 比 500 只贵 0.05 ms；
3. §7 的猜想被证实：程序化机械动画**应该放进 Shader**，
   靠 `INSTANCE_CUSTOM` 携带每单位相位，CPU 每帧每单位只写一个 Transform。

**中型敌人（§4.2，同屏 10–30）和 Boss（§4.3，1–3）继续用传统 Node 即可。**
按实测的 6.4 µs/单位，30 个中型敌人约 0.2 ms，完全不值得为它们做数据化改造 ——
而它们恰恰需要 Node 带来的灵活性。

## 7. 这个结论的适用边界（必须写下来，否则会被误用）

1. **MultiMesh 没有逐实例视锥剔除。** 整个 MultiMesh 只有一个 AABB，
   屏幕外的单位照样提交给 GPU。在 60×46 m 的固定镜头竞技场里无所谓
   （16,000 单位 GPU 也才 1.17 ms），但**换成大世界就必须按空间分块成多个 MultiMesh**。
   Node 版本反而是自动剔除的，这是它唯一的结构性优势。
2. **一个 MultiMesh = 一个网格 + 一个材质。** 敌人种类要么各用一个 MultiMesh，
   要么把差异塞进 `INSTANCE_CUSTOM`（目前 4 个浮点里只用了 2 个：相位、生死）。
3. **本轮完全没测碰撞和物理。** 给每个单位加碰撞体很可能把 Node 式的开销重新引回来，
   这是在正式采用架构前**下一个该测的东西**。
4. **需要逐单位骨骼动画的话，这套方案不成立。** 但 §7 本来就要求小兵避免骨骼动画。
5. **仍然是开发机数据**（RTX 5080 Laptop）。§11 的目标硬件验证尚未进行 —— 见 §8。

## 8. 尚未关闭的风险：目标硬件

M1–M5 的所有性能数字都来自 RTX 5080 Laptop。§11 明确要求在
Intel Iris Xe / AMD 680M / 780M 一级的集显上验证，§33 的 Go/No-Go 的 C 项依赖它。

**这一项目前没有设备，属于未关闭的风险。** 好消息是复跑成本极低：
把项目拷过去，一条命令，结果自动写 CSV。

同时基于 M4/M5 的实测可以给一个有依据的预判（而不是猜测）：
群体部分的瓶颈是**单线程 CPU**，不是 GPU（16,000 单位时 GPU 才 1.17 ms），
所以集显本身不太可能卡在群体上；真正会被集显卡住的是 §23 的 VFX 压测 ——
overdraw、透明层数、粒子填充率。**下一步的重点应该放在那里。**
