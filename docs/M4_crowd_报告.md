## 1. 测量方法

- 场景：`scenes/PerformanceBenchmark.tscn`（按 §25 从视觉场景拆出的独立副本）
- 每个测量点：关 V-Sync → 设定数量与阴影模式 → **预热 5 秒 → 采样 20 秒**
- 平均值与 1% low（第 99 百分位帧时）分开记录

- 敌人逻辑严格保持 §22 的最简形态：Spawn → Move → Hit → Death，

- 硬件：NVIDIA RTX 5080 Laptop，1886×1061，Forward Mobile

> 结论要在 Iris Xe / 680M / 780M 上复测。

## 3. 核心结论

### 3.1 完全是 CPU 瓶颈，几何量不是问题

**2000 个敌人 + 全部投影时，GPU 渲染时间只有 0.82 ms，而整帧是 14.31 ms —— GPU 占不到 6%。**

从 100 到 2000（20 倍），GPU 时间只从 0.36 涨到 0.82 ms，帧时却涨了 20 倍。
§5 的预判被实测证实：**"面数本身预计不是主要瓶颈"是对的**，
真正的开销在 Node 数量、draw call 提交和 Transform 更新。

这条结论直接决定了后续优化的方向：压面数（300→150）几乎没有收益，
减少 draw call 和减少逐单位 CPU 工作才有收益 —— 也就是 M5 要验证的 MultiMesh 路线。

### 3.2 draw call 随数量线性增长，而且是每单位 5 个

传统 Node 架构下每个敌人是 5 个 `MeshInstance3D` = 5 次 draw call；
开启投影后阴影 pass 再翻一倍：

    2000 敌人 + 阴影A = 19,938 draw calls

这就是 M5 的目标：MultiMesh 应该把"每单位 5 次"变成"每部件 1 次"，即总共约 5 次。

### 3.3 §17 阴影问题：有明确答案了

以 1000 敌人为例：

| 模式 | 帧时 | 相对 B 的额外开销 |
|---|---|---|
| B 不投影 | 3.82 ms | — |
| C blob 假阴影 | 4.64 ms | +0.82 ms（+21%） |
| A 真实投影 | 6.07 ms | +2.25 ms（+59%） |

**blob 假阴影的代价只有真实投影的约 36%**，而且它仍然提供了物体与地面的接触感。
§17 的建议成立：小兵不应该投真实阴影。建议 Preset 映射为
Low/Medium = C（blob），High = 可选 A。

注意 C 比 B 贵是正常的：它多了一层 MultiMesh 和每单位一次透明混合的四边形（overdraw）。

### 3.4 逐单位 CPU 更新的量级

冻结更新循环（只保留场景树和渲染）：

| 1000 敌人 / 阴影 B | 帧时 | draw calls |
|---|---|---|
| 逻辑运行中 | 3.82 ms | 5,135 |
| 逻辑冻结 | 1.09 ms | 3,749 |

**但这个对比有偏差**，必须说明：冻结后敌人不再向玩家移动，会停留在外围生成圈上，
更多单位被视锥剔除（draw call 5135 → 3749）。所以 2.7 ms 的差值里混了"少画了 1400 次"的部分，
不能全部算作更新循环的开销。要干净地拆开需要固定可见单位数再测一次 —— 已记为 M5 的待办。

即便如此，量级是清楚的：GDScript 里逐单位改 3 个子节点的 Transform，在 1000 单位规模上是**毫秒级**的项目。

### 3.5 `process_ms` 这一列暂时不可信

CSV 里的 `process_ms`（来自 `Performance.TIME_PROCESS`）在多行上大于实测帧时，
冻结逻辑那一行甚至是 5.68 ms 对 1.09 ms 的帧时 —— 自相矛盾。
在弄清这个监视器的语义之前**不要用这一列下结论**；
帧时和 GPU 时间来自各自独立的测量，是可信的。

## 4. 对照 §12 的性能目标

§12 的优先目标是 1920×1080 / 60 FPS / 500–1000 敌人。在**这台开发机**上：

- 1000 敌人 / 阴影 B：262 FPS 平均，176 FPS 1% low
- 2000 敌人 / 阴影 B：97 FPS 平均，85 FPS 1% low
- 即使 2000 敌人 + 全部真实投影也有 70 / 64 FPS

也就是说传统 Node 架构在开发机上就已经越过了 §12 的门槛。**但这不构成通过**，原因有二：

1. §11 明确不允许用开发机判断，而且**因为瓶颈在 CPU**，
   目标硬件的结果主要取决于单线程 CPU 性能，而不是那块集显 ——
   这一点和直觉相反，值得单独注意：集显机器的 CPU 往往并不弱，
   所以群体测试在目标硬件上的表现可能比担心的好；
   真正会被集显卡住的是 §23 的 VFX 压测（overdraw / 透明层），那是另一回事。
2. 本轮**完全没有 VFX、没有武器、没有物理**。真实战斗要在这个基础上叠加。
